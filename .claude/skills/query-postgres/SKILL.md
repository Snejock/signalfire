`rss-fetcher` читает/пишет две таблицы Postgres — `dds.r_rss_feeds` (список лент, которые он
опрашивает) и `ods.rss_news` (загруженные статьи, по ним вычисляется курсор возобновления).
Начиная с базы `signalfire` на `dwh-pg-1` этот репозиторий сам владеет своей схемой Postgres —
миграции обеих таблиц лежат в `dwh/migrations/pg/` этого репозитория (см. «Таблицы signalfire»
ниже и `./dwh/README.md`).

Postgres недоступен локально — он существует только внутри Docker-контейнера `dwh-pg-1` на
`loki` (см. `connect-servers`). Весь доступ идёт через SSH + `docker exec`.

## Подключение

Каноническая команда — брать пользователя/базу из окружения самого контейнера, а не хардкодить
креды в файле, который лежит в git:

```
ssh loki "docker exec -i dwh-pg-1 sh -c 'psql -U \"\$POSTGRES_USER\" -d \"\$POSTGRES_DB\" -c \"...\"'"
```

- Хост: `loki` (только SSH, локального туннеля/проброса портов нет)
- Контейнер: `dwh-pg-1`
- `POSTGRES_USER` / `POSTGRES_DB` / `POSTGRES_PASSWORD` уже заданы как переменные окружения
  внутри контейнера (заполняются из `.env` на `loki` через `dwh/compose/postgres/docker-compose.yaml`),
  так что реальное значение логина/пароля никогда не должно появляться ни в команде, ни в этом
  файле. Флаг пароля не нужен — локальная socket-аутентификация внутри контейнера ничего не
  спрашивает.

Добавьте `Bash(ssh loki *)` в `.claude/settings.local.json`, чтобы это выполнялось без запроса
подтверждения.

## Запуск запросов

- **Однострочные запросы** — `sh -c '... -c "..."'` как выше. Кавычки вложены на три уровня
  (внешние двойные для SSH, одинарные `sh -c '...'`, и сам SQL), так что для запроса со своими
  строковыми литералами проще сразу перейти на heredoc-форму ниже, чем жонглировать экранированием.
- **Многострочные / сложные запросы** — передавать SQL через stdin heredoc'ом, а не бороться с
  экранированием в `-c`:

  ```
  ssh loki "docker exec -i dwh-pg-1 sh -c 'psql -U \"\$POSTGRES_USER\" -d \"\$POSTGRES_DB\"'" <<'SQL'
  select feed_nm, is_active, interval_sec
  from dds.r_rss_feeds
  order by feed_nm;
  SQL
  ```

  (Именно флаг `-i` у `docker exec` вместе с heredoc'ом позволяет многострочному SQL корректно
  дойти до psql. Строковые литералы SQL внутри heredoc'а можно писать обычными `'...'`, так как
  внешняя оболочка их не трогает.)

- **Чистый/парсируемый вывод** — полезные флаги psql: `-t` (без заголовков/футеров), `-A`
  (без выравнивания), `-F','` вместе с `--csv` для CSV, `-P pager=off`, чтобы не завис пейджер,
  `-x` для расширенного вывода на широких строках.

## Изучение схемы

- `\dn` — список схем
- `\dt dds.*`, `\dt ods.*` — список таблиц в схеме
- `\d dds.r_rss_feeds`, `\d ods.rss_news` — описание колонок, типов, индексов

## Таблицы signalfire

| Таблица | Роль |
|---|---|
| `dds.r_rss_feeds` | Справочник RSS-лент, которые опрашивает `rss-fetcher` — по одной asyncio-задаче на каждую активную строку (`is_active`), интервал опроса — `interval_sec`, курсор возобновления — из `ods.rss_news`. Загружается в `Application._load_feeds_from_db` (`services/rss-fetcher/packages/Application.py`). |
| `ods.rss_news` | Загруженные статьи (сырой слой). `rss-fetcher` только читает эту таблицу (чтобы вычислить `max(published_dttm)` по каждой ленте как курсор возобновления) — сам он в неё не пишет. Писать сюда должен стрим Redpanda Connect (`dwh/rpc/ods/`), который потребляет топик `SGN_RSS_NEWS_RAW`, куда публикует `rss-fetcher` — на момент миграции на собственную базу `signalfire` этот стрим ещё не перенесён сюда из `chronica` (там он читал топик `CHR_RSS_NEWS_RAW` и писал в общую `core`), `dwh/rpc/` в этом репозитории пока пуст. |

Обе таблицы следуют общей DWH-конвенции именования (`ods` = сырые данные, `dds` = ядро Data
Vault, `bds`/`dm` — дальше по цепочке), подробно описанной в `../chronica/CLAUDE.md` → «DWH:
schemas and naming» (общий для всех DWH-проектов документ, не копируется сюда).

## DDL и запись — вне зоны ответственности

Этот скилл только читает. Схема `dds.r_rss_feeds`/`ods.rss_news` теперь описана миграциями в
`dwh/migrations/pg/` **этого репозитория** (собственная база `signalfire`, не общая с другими
проектами — см. `./dwh/README.md`), но сам скилл всё равно не пишет и не меняет схему. Если
задача требует `INSERT`/`UPDATE`/`DELETE`/`DROP`/`TRUNCATE` или изменения схемы — не выполнять
это напрямую в продовой БД, а добавить/изменить миграцию в `dwh/migrations/pg/`.
